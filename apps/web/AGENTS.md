# Durable-DAV-Router — Web SPA

Scope: `apps/web/**`. Parent index: `../../AGENTS.md`.

- Vite + React 19 SPA (`src/main.tsx`: `BrowserRouter` → `SpaApp`). Build embeds `dist/index.html` into `apps/api/src/generated/spa-shell.ts` (Vite plugin `spa-shell-embed`; never edit generated file; `scripts/ensure-spa-shell-stub.mjs` creates the empty stub on install).
- **Rebuild before deploy: `pnpm run build`.** The API worker serves `SPA_HTML` from the *last local build*, and both `dist/` and `apps/api/src/generated/` are gitignored — so a source fix here is inert until `vite build` runs again. `scripts/verify-spa-shell.mjs` (in `pnpm run checks`) rejects a missing/stubbed/mismatched artifact. It cannot detect a stale-but-self-consistent pair, which is why the rebuild is an operational duty, not just a checked one.
- **The bucket browser's contract with the backend is path addressing.** `lib/davXml.ts` strips the `/<owner>/<volume>` base from `DAV:href` (RFC 4918 §8.3) to recover the volume-relative `path`; `services/davClient.ts` turns that `path` straight back into a request URL. The router forwards upstream 207 bodies verbatim, so nothing strips the base in transit. Both halves must agree: an href format change on the backend silently breaks every folder click and download here, because the volume root stops being recognised as the self-response and every path comes back double-prefixed. Always pair "parse a real 207 body" with "use the parsed `path` in a real request" — a disagreement is invisible when either half is checked alone. `test/web-davxml.test.ts` and `test/web-davclient.test.ts` are that pair.
- `?path=` is user-supplied and reaches `davClient.entryUrl`, so `VolumeView.cleanPath` drops `''`/`.`/`..` and any segment containing `/` or `\`, and `entryUrl` filters dot segments again and fails closed on a base escape. `encodeURIComponent` leaves `.` alone, so without both layers `?path=../../admin` resolves to `/user/volumes/<owner>/admin` — outside the volume.
- `?backend=` (the upstream selector) has **one** implementation, `lib/backendSelector.ts` — it was five across `services/*` (a param map, two string helpers, two inlined template literals) and `apps/web/AGENTS.md` used to name each of them. `test/web-services.test.ts` now pins the *contract* instead of the shapes: every service emits the selector exactly once, correctly encoded, and emits no query at all when none was named. A dropped selector silently targets the wrong backend, or — with an empty value — none at all. It is also threaded as a `backend` prop through `VolumeView` → `VolumeFileList`, because the download `href` is the one request in the bucket browser built inline in JSX: when it omitted the selector, every download 409'd (`selectBackend` cannot resolve an ambiguous volume) and the browser saved the JSON error body as the file. `test/web-volume-file-list.test.tsx` asserts the `href` carries it, and that an absent `backend` produces no `?backend=` at all.
- **Paged browse is backend-optional, and `X-Dav-Page-Count` is the absence signal.** `listDirectory` returns a `DavListing` (`entries` + `page`/`limit`/`total`/`paged`) rather than a bare array, and requests `?page=&limit=` alongside the selector. A backend that predates paging returns the whole listing with no such header; the pager then renders nothing instead of implying pages that do not exist. So this SPA works against any backend and a new SPA against an old backend degrades to the previous behaviour. The URL join must respect the `?backend=` that `entryUrl` already appended — a second `?` silently drops the paging parameters, and the symptom is a pager permanently stuck on page 1. Page state lives in `?page=` (shareable; resets to 1 on a folder change), page size in `localStorage` (a preference, not navigation state), and both are clamped on read because both are user-supplied. `lib/davPage.ts` deliberately duplicates Durable-DAV's clamps: the router reaches a backend over HTTP and links to no server source, so the local copy is the only thing the root suite can assert.
- `SpaApp.tsx` — thin composition root: `useCurrentUser` + `useSpaLanguage` + `useNotice` hook slices, `Header`/`NoticeBar`, then `SpaViewRouter` (no data fetching in router).
- `components/layout/SpaViewRouter.tsx` — routes: `/` (Dashboard or Landing), `/new` (gated `NewVolumeView` with backend selector + auto-loaded read-only owner), `/backends/new` (gated `NewBackendView`), `/:owner/:volume` (`VolumeView`, backend in `?backend=` + subpath in `?path=` so deep file URLs never collide with WebDAV `GET`, settings in `?tab=settings`), `/settings` (user settings + `BackendsSettingsCard`), `*` (localized 404 `Card`). Views in `src/views/`; shared `ui/` primitives in `src/components/`.
- API access: `src/lib/api.ts` + `src/services/*` (`backend/volume/credential/userService`) + `src/lib/davXml.ts` (PROPFIND multistatus parser) + `src/lib/davPage.ts` (page/size clamps + page-count math) + `src/services/davClient.ts` (PROPFIND/GET/PUT/MKCOL/DELETE/COPY/MOVE over `/user/volumes/:owner/:volume/files` browser plane with `?backend=`, and `?page=`/`?limit=` for the pager).
- **The backend registry lives in `/settings`, and the dashboard shows buckets only.** `src/components/settings/BackendsSettingsCard.tsx` absorbed the dashboard's Backends section, so it carries both halves: the edits (display name, delete) and the liveness view (status, on-demand probe). Its status line reads `last_status`/`last_seen_at` off `GET /user/backends` — **not** the `GET /user/volumes` fan-out that used to paint the dashboard's health badges. That fan-out is a live probe of *every* backend from Worker egress, so rendering it on a settings page load would spend a probe per backend to draw one line, and `last_status` is what the row's Check button refreshes anyway. `lastSeenAt` is epoch **seconds** (`BackendService.recordProbe` → `getCurrentUnixTimestampInSeconds`), so it is multiplied by 1000 before display; read raw, the same number renders as January 1970 and still looks like a date. Check appears on **every** row, not only on a failing one — the dashboard gated it on the fan-out's `ok` flag, and this card does not make that request, so gating it would hide the only way to get a fresh answer. Unregistering a backend goes through `ConfirmDeleteModal` (not the type-to-confirm the bucket delete uses): it deletes no data, and the cost of a mis-click is the `backend_username` cache the WebDAV route keys on. The dashboard's empty-bucket state links to `/settings` for first-run discoverability, unconditionally — deciding whether to show it would need the backend list back on the dashboard. Dashboard: `src/views/DashboardView.tsx` (buckets grouped by backend, one `listMyVolumes` request); per-bucket settings: `src/components/volume/VolumeSettingsTab.tsx` (description + visibility + Danger Zone delete, all `backend`-aware) + `VolumeCredentialsCard.tsx` (proxied per-bucket Basic credentials, copy-once password, read-only checkbox at creation + a per-row Make Read-Only / Allow Writes toggle) + `HrefPrefixModeCard.tsx` (Link Prefix: the backend's `base` | `root` `DAV:href` anchoring, proxied through the unreshaped `/user/volumes` JSON) + `VolumeReplicationCard.tsx` (Replication: scheduled two-way WebDAV sync to another server or a sibling bucket — composed from `VolumeReplicationForm`/`Row`/`Decisions` and served by `services/replicationService.ts`). `Volume.hrefPrefixMode` is optional (a backend predating the setting omits it) but `VolumeDetail.hrefPrefixMode` is required, because `toVolumeDetail` resolves an absent value to the conforming `base` in one place.
- **Replication is a proxied backend feature, and the SPA models only what it displays.** `services/replicationService.ts` is the whole client: eight calls over `/user/volumes/:owner/:volume/replications*`, each threaded with the trailing `backend` selector, plus two pure render helpers (`intervalLabel`, `targetLabel`) that are unit-tested from the root suite. The card fetches through `useAsyncLoad` rather than hand-rolling a cancellation guard, tracks a single `busyId` rather than one boolean (a slice runs for tens of seconds, and a global flag would grey out every other target's controls), and keeps `backend` on every mutation — a dropped selector here 409s, or silently addresses the wrong backend, and reads to the user as "you have no targets".
- **`listReplications` answers a question, not a request.** It returns `{ supported: false }` on a `404` instead of throwing, so version skew is a rendered state rather than an error. Two things make that sound and both are easy to break: the card is gated on `VolumeSettingsTab`'s `detail && …` (which is what proves the bucket exists and is owned — Durable-DAV answers `404` for a foreign volume too), and the decision is made on `getBackendErrorStatus` rather than the error type, which is `NotFound` for both a missing bucket and a missing route. `getBackendErrorStatus` was added to `lib/api` for this: `status` was previously reachable only by reaching into `BackendError`'s shape at the call site.
- **Two i18n shapes are load-bearing in this card, and both are checker-driven.** Mode labels and mode help are `{ value: 'ns.key' }` / `{ key, text }` maps rather than template literals: `scripts/i18n-coverage.ts`'s `computedKeySites` fails `validate:locales` on any interpolated `t()` argument, and its key extractor only recognises a literal following a colon, so a `[key, text]` tuple reads as an orphan. That check is a plain regex over source text **including comments**, so a doc comment that writes the offending shape out in code font is itself a build failure. `replication` is in `KEY_NAMESPACES` for the same reason — an unlisted namespace makes every key look like prose and the coverage check silently passes on nothing.
- **The decision panel closes on a failed load, and says why.** `loadConflicts` clears the panel and reports the error rather than leaving an empty list up: an empty list reads as "nothing to reconcile", which is a claim about a target's audit trail that was never verified. The ported Durable-DAV behaviour swallowed that failure into a bare `catch`, which left the owner clicking "Show Decisions" against a target already refusing with nothing to indicate why.
- The credential read-only flag is **backend-owned**. The router stores no credentials and enforces nothing, so `VolumeCredentialsCard` only carries it: `createBucketCredential(..., readOnly, backend)` sends it, `setBucketCredentialReadOnly` flips it via `PATCH` on the already-proxied `/user/volumes/:owner/:volume/*` path, and the card never decides an access level itself. `readOnly` sits **before** the trailing `backend` selector — appending it after would let `true` become `?backend=true` and 404 as a missing bucket instead of reporting the access level. The toggle is optimistic with a revert, because the credential is a bearer secret the client already cached: the backend cannot make the client forget it, so the flag takes effect on that client's *next* request, not as a revocation.
- i18n: `src/i18n.ts` (i18next + `react-i18next`) — `SUPPORTED_LANGUAGES` (English-only today; grows bundle-by-bundle under `src/locales/<tag>/translation.json`, enforced by `pnpm run validate:locales`), single `canonicalizeLanguageTag` + `normalizeLanguage`, `detectInitialLanguage` (stored `durable-dav-router-lng` → `navigator.language` → `en`), `loadLanguage` (static `import.meta.glob` per-locale chunks, falls back to `en` for unshipped bundles).
- English UI text uses Title Case. Pure helpers are unit-tested from the root suite (`src/lib/davXml.ts` via `test/web-davxml.test.ts`, `src/services/davClient.ts` via `test/web-davclient.test.ts`, `src/services/*` via `test/web-services.test.ts`). The logic-bearing layers (`src/lib`, `src/services`) are inside the coverage gate; `src/components/**` and `src/views/**` are measured but at 0% and are named as follow-up in `vitest.config.mts`.
